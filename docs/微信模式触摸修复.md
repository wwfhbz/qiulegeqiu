# 微信小游戏模式切换触摸修复

基线：main `9cb3520`（PR45已合并）。只修复微信输入和模式切换保护，不开发社交功能。

## 诊断与复现

`modePicker → Panel.draw → Panel.tap → chooseMode → Game.setMode` 的业务调用存在，画面与命中矩形也来自同一份布局。已确认的输入缺陷：

1. `down/move` 只读 `clientX/clientY`。带 `x/y` 或 `pageX/pageY` 的输入无法命中，坐标会成为undefined；旧测试只提供client坐标，未覆盖该路径。
2. 任何移动超过8个CSS像素都被视为拖动，即使仍在58像素高的模式卡片内也会取消选择。用起止相差10×2像素的触摸可稳定复现按钮无响应。
3. `chooseMode` 本身没有进行中对局保护，只有菜单入口作判断；如果被其他入口调用，可能未经确认重置对局。
4. 面板切换时旧命中表一直保留到下一帧；释放触摸也未检查是否仍在按下的按钮内。

同一新增回归文件放到基线独立worktree运行：**11/11失败**；修复后11/11通过。没有真机事件抓取，不能断言线上运行时使用哪一种字段或线上所有故障仅由这些路径造成。

## 最小修改

- `wechat-game/src/TouchPoint.ts`：统一取得有限数值坐标，优先client，再兼容x/y及page；所有坐标保持屏幕CSS像素，**不乘除DPR，不减安全区**，与Canvas命中区域一致。
- `Platform.ts`：触摸类型明确描述可选的兼容坐标字段。
- `App.ts`：down/move/up共用坐标读取；模式卡片允许18px轻微移动，其他拖动阈值仍8px；释放点和按下点必须命中同一个控件。chooseMode拒绝忙碌、排行榜加载中或尚未结束的对局；结束后正常切换，原HUD/生命/榜单/存储更新保持原路径。
- `Panel.ts`：show时立即清空旧命中表；tap验证按下/释放位于同一按钮。
- `tests/wechat-mode-touch.test.ts`：9组尺寸/DPR/坐标形态的闯关→无尽→闯关真实触摸；检查actual game.mode、5/3生命、12/1关卡配置、endless物理场、HUD及榜单模式；另测取消、非法输入、释放越界和进行中/暂停保护、结算后切换。
- `tests/browser-wechat-alignment.mjs`：五种手机尺寸通过wx回调执行三次切换，包含x/y输入和轻微移动，直接断言game.mode。

不改Layout、Game、关卡、物理、计分、道具、排行榜、登录、规则版本和server。
