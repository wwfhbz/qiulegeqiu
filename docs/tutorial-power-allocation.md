# 第一、二关预分配道具

## 配置与统计口径

`src/Levels.ts` 选择 `src/BrickPowerRules.ts` 的关卡配置。分配对象为 `Blocks.reset()` 生成后 alive=1 的可破坏砖块，第一关600、第二关1200，布局、球速、出口和挡板不变。这两关没有特殊砖、不可破坏砖或多次击打砖。

| 关卡 | 总砖数 | X3砖 | 加宽砖 | 无道具砖 |
|---|---:|---:|---:|---:|
|轻松出击|600|480|0|120|
|渐入佳境|1200|360|240|600|

配额采用四舍五入：道具数=round(砖数×比例)，X3数=round(道具数×X3份额)，加宽数=道具数−X3数。无道具数=总砖数−道具数，不能分别四舍五入后产生总量差。

生成时按空间相邻的每10块有效砖分层，给每层分配累计整数配额并进行种子洗牌。实际两关每10砖分别有8个X3，以及3个X3+2个加宽。具体位置随每局种子变化，同一种子可由客户端与服务端一致重建。`Blocks.powerKinds` 使用Uint8Array记录：0无道具、1 X3、2加宽。

`Blocks.hit` 的存活检查保证重复碰撞不会重复掉落。道具砖击碎只生成掉落物，仍必须接到挡板才生效；漏接消失。普通丢命保留砖块及其分配表，清理残留掉落和加宽效果；新游戏重新分配。

## 池容量与后续关卡

旧道具池只有24格，满池时会静默不生成新物体。本次仅给预分配关卡预留本关全部奖励的容量：480和600格，确保同帧击碎也不丢掉奖励。并非只承诺逻辑分配数量；测试检查实际活跃掉落数及唯一ID。

第三至十二关没有新增预分配配置，保留原间隔14/28、概率权重、24格容量、机关和难度。预分配使用独立随机流；仍按旧间隔推进原随机流，保证相同种子及相同击碎顺序下，第三至十二关原有道具类型序列也不变。

X3继续使用共享 `PowerRules.tripleTarget`：≤20球乘3，>20球增加3，最多100球。未改变父球派生、速度、方向散开、物理和特效。

## 验证范围

- 50个种子逐关核对精确配额、空间分层、确定性及不同种子的变化。
- 同帧击碎整关砖，实际生成480/600个掉落；重复击碎不重复生成。
- 漏接无效果、真实挡板拾取、20/21阈值、100上限、丢命保留分配。
- Web/微信同种子配额和日志一致；原十关随机序列和容量不回归。
- 真实道具回调生成的密集挑战日志，通过本地隔离API的Cookie和微信Bearer身份提交；校验伪分、伪造/重复/提前拾取、幂等重试及旧成绩行不变。

微信构建和宿主模拟测试不等于微信开发者工具或低端安卓真机验收；正式发布前仍需设备测试。测试不访问生产数据库。

## 已确认的统一重赛上榜策略

用户已确认采用独立规则重赛，不把不同难度的原始分数混排，也不换算旧分。

- 当前规则：`1.3.0-arcade-5l-12lv-drops-v2`，使用新版600/1200砖固定配额。首条launch必须同时有 `brickPowerVersion:2` 和 `tripleRuleVersion:2`，后续不得更换。
- 旧十二关：`1.2.0-arcade-5l-12lv-v1`，使用冻结的 `PREVIOUS_LEVELS`、旧掉落间隔/权重/24格池，兼容X3更新前后两种日志。禁止用新预分配日志冒充旧规则。
- 旧十关：`0.8.0-arcade-5l-10lv-v1`，保留原校验。

全球TOP100和“我的排名”仅查询当前规则已验证、非调试成绩。只有旧成绩的玩家如实显示未上榜；重新挑战提交新版有效成绩后进入全球榜。不新增赛季切换或重复排行榜入口。

历史成绩、身份、会话及微信绑定不删除、不迁移、不换算。`/api/me?board=global` 和 `/api/me/best?board=global` 增加 `historicalBests`，分别返回旧十二关及旧十关的个人最高有效成绩，保留 `historicalBest` 供旧调用兼容。网页个人记录区和微信菜单“个人历史记录”使用同一文案格式。旧版显式rulesVersion查询和提交继续可用。已有reset-epoch数据库也继续接受旧十二关客户端；不会借此恢复已失效的旧身份。

后端health及创建挑战响应声明所有可接受版本、协议2及 `tutorial-brick-powers-v1` 能力。新客户端检查能力，旧客户端仍可按旧规则提交；旧客户端无法展示新版全球榜时需刷新到新版，不会将新版分数伪装为旧榜。

## 安全部署及回退（只提供说明，尚未执行）

无数据库结构迁移；复用原有规则版本列和分版本最佳引用。代码修复了旧版refreshBest依赖“当前版本常量”的查询，改为按所属版本精确查找，防止新旧最佳引用相互覆盖。

原发布脚本禁止跨规则直接覆盖，以防新成绩落库后回退到不认识它的验证器。该安全检查保留；仅为本次明确的1.2→1.3升级增加显式的兼容API桥接模式。两个步骤使用**同一个已审核、校验完整性的发布包**，均须另行获得生产部署确认。

```bash
# 生产上仅在获得部署批准、核验发布包SHA256和源码提交、确认环境后执行。
# 以下RELEASE_DIR指已核验的解压目录，不是源码工作目录。
sudo bash "$RELEASE_DIR/deploy/publish.sh" --apply "$RELEASE_DIR" --api-only
# 第一阶段保留现有HTML和assets，仅安装兼容旧/新规则的后端。
# 核对 /api/health 支持两个十二关版本和新道具能力后，才继续：
sudo bash "$RELEASE_DIR/deploy/publish.sh" --apply "$RELEASE_DIR"
```

第一阶段同样执行在线备份、生产用户依赖解析、实际候选启动和健康检查，失败恢复旧API，不覆盖数据库。它不写网站HTML或assets。未知跨版本或旧十关直接升级仍拒绝，不得用重置参数绕过检查。

第二阶段的回退目标已是兼容新旧规则的API。失败只回退API指针和HTML，保留数据库及所有已提交的新成绩。成功后若只撤回前端，也必须保留这个兼容后端，不能直接退回原始只懂1.2的API。桥接期间旧网页仍可提交旧成绩，全球榜查询会要求刷新新版；完成第二阶段即恢复新版榜单体验。微信客户端应在兼容后端和网页验证完成后更新。

该模式不修改Nginx、系统Node、防火墙或《统帅三国》；本次开发没有连接生产服务器。
