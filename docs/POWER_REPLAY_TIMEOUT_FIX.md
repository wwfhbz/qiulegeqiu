# 部署门禁：100种子道具回放测试超时修复

## 真实定位

实际文件是 `server/tests/power-replay.test.ts`，部署在server目录执行Vitest时显示为 `tests/power-replay.test.ts:27`。本修复独立基于main的5ec1854，不夹带尚待审核的UI改版。

该用例对seed=1～100分别执行完整真实规则夹具：清空前两关进入第三关，4800个固定步长的日志/积分/真实道具池更新，约2400次确定性击砖、真实拾取与多球，再逐轮漏球直至Game Over，最后逐个执行服务端verifyTrace。100组总计480000个夹具步和438386条事件。

循环均有明确边界，没有网络请求或外部服务等待；本机所有100组都能结束、服务端校验通过。修改前单独运行四个回放用例，其中目标用例实际3952.44ms，已经接近Vitest默认5000ms。不能把本机通过解释为腾讯云也一定在5秒内完成；生产机器CPU/负载未实测。

发现真实的夹具无效开销：每一步都会filter/sort寻找最近道具，但默认第三关实际使用固定挡板轨迹，该结果只在第四关及之后才会被使用。100组第三关样本白做了480000次数组分配/排序。该部分属于测试夹具，不是游戏或生产验证器需要的工作。

最近固定配额增加了合理工作量：原前两关只有floor(600/14)+floor(1200/14)=127次间隔掉落尝试，且池上限24；新配置为480+600=1080个真实掉落，夹具还必须生成这些物体并让回放严格检查。不能为了变快而恢复旧道具配置、缩减种子或关闭验证。CPU采样显示工作集中在同步夹具构造、数组回调/垃圾回收及verifyTrace，未发现卡死。

用户报告的部署退出码55没有在当前仓库中发现直接的exit55映射，可能来自外层部署包装；本次没有访问生产机、没有改退出码或让脚本忽略失败，修复的是实际失败的测试门禁。

## 最小修复

只修改 `server/tests/power-replay.test.ts`：

1. 第四关及之后才计算最近道具；第三关不执行不会使用的filter/sort。原挡板轨迹、随机数消费、掉落/拾取、死亡和校验逻辑不变。
2. 仅100种子用例使用第三个参数30000ms，其余用例和全局配置保持默认时限。30秒是批量压力回放的有限预算，不是生产API超时。

生产Game、Physics、PowerRules、PowerUps、Levels、ChallengeJournal、ScoreSystem、verifier、API、数据库和部署脚本均未修改。

## 修改前后实测

同一台本地Linux、Node.js24.19.0；每轮都运行整个回放文件的4项测试，并非只跑一个简化样本。表中为目标100种子用例的Vitest记录。

| 运行 | 耗时 | 文件内用例 |
|---|---:|---:|
| 修改前 | 3952.44ms | 4/4通过 |
| 修改后连续第1次 | 2955.99ms | 4/4通过 |
| 修改后连续第2次 | 2658.54ms | 4/4通过 |
| 修改后连续第3次 | 2614.66ms | 4/4通过 |

三次平均约2743.06ms。时间随机器、JIT和负载波动，这不是服务器性能保证。单独的诊断脚本还对修改前后100组完整日志和校验摘要做SHA256比较，100/100完全一致。[原始耗时及逐种子摘要](power-replay-timeout-results.json)。
